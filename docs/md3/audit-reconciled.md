## Scope, evidence, and interpretation

Product intent: `AGENTS.md` and `docs/frontend-spec.md`, especially §§3–5 and §10. References: `docs/ref/md3/INDEX.md` and the captured official pages dated 2026-11-15. Hark's input is `/workspace/work/rofu-md3/hark_audit.md` (58 findings, H-001–H-058), reviewed after Sol's original 70 findings were drafted; its additions and disagreements are adjudicated below. This is a reconciliation by Sol against both evidence sets, not a claim of subsequent Hark sign-off. All source locations below are repository-relative; multiple locations in one row identify instances of the same finding, not separate findings. Category numbers follow the task: 1 color/theme, 2 typography, 3 shape, 4 elevation, 5 motion, 6 components, 7 layout/targets, 8 states, 9 accessibility, 10 iconography.

Severity: **high** means a substantial access or interaction risk; **med** means a material component, layout, or design-system inconsistency; **low** means a limited visual inconsistency or consolidation opportunity. “Product requirement” and “migration recommendation” are identified where the official guidance permits alternatives. A static risk is explicitly described as such; a literal color is not automatically a measured contrast failure.

Flutter sources were inspected read-only under `/workspace/tools/flutter/packages/flutter/lib/src/material`, including `icon_button.dart`, `button_style_button.dart`, `drawer.dart`, `popup_menu.dart`, `list_tile.dart`, `dialog.dart`, `dialog_theme.dart`, `bottom_sheet.dart`, `slider.dart`, `progress_indicator.dart`, and `page_transitions_theme.dart`. No Flutter command that could generate repository files was run. No network calls, code edits, builds, tests, or screenshots were needed for this source audit.

Important interpretation decisions:

- `docs/ref/md3/develop__flutter__overview.md` §Material 3 Widget catalog explicitly says Flutter supports original M3 and does not provide the full Expressive catalog. Missing Expressive-only widgets are not automatically application defects. Baseline M3 variants remain legitimate migration targets.
- `docs/ref/md3/styles__shape__corner-radius-scale.md` §Corner radius scale includes **20, 32, and 48dp** as well as the requested original scale. The existing 20dp user bubble is both a current M3 token and an explicit frontend-spec §3.1 requirement. Preserve it as a named component token. Circle/avatar radii express a full circle, not arbitrary rectangular corner tokens.
- `docs/ref/md3/styles__elevation__tokens.md` §Tokens deprecates surface tint. Do not “fix” this app by restoring tint overlays or adding shadows everywhere. Surface container roles do not have a mandatory one-to-one mapping to elevation levels (§Surface color roles & elevation in `styles__elevation__applying-elevation.md`).
- Static seeded color is valid M3. Android dynamic color is a missing **product feature** from frontend-spec §5, not an M3 prerequisite. Raw seed previews and brand artwork are legitimate source colors; their foregrounds still need contrast.
- `Colors.transparent`, theme seed constants, and intentional AMOLED black are not themselves semantic color violations. Custom AMOLED neutrals should stay in the theme and be tested with paired on-colors; black mode is explicitly authorized by frontend-spec §10.
- M3 allows density customization and custom components. The issue is ungoverned defaults, lost accessibility, or mismatched component anatomy, not the mere presence of a `Container`, `InkWell`, or dense content.

## Proposed shared foundation

Design proposal only; no module is created by this report. Keep appearance serialization compatible, separating stored preferences from resolved theme objects. A future `core/design/` module could contain:

- `app_theme.dart`: color-source resolution, seeded light/dark themes, AMOLED policy, TextTheme, component themes and PageTransitionsTheme.
- `app_tokens.dart`: spacing, corner-shape, elevation and nonlinear motion tokens; explicit watch/bubble/status exceptions.
- `app_typography.dart`: role-based text styles, code style and watch base overrides, preserving system TextScaler.
- `app_semantic_colors.dart`: ThemeExtension for warning and other product-only roles, with tested paired foregrounds. Seed/brand data remains distinct from UI semantic colors.
- `adaptive_layout.dart`: five window-width classes plus an independent watch predicate, pane widths and content margins. Do not use window width as a substitute for mouse/touch input origin.
- Shared presenters for action menus/sheets and editors, accessible icon/selection controls, card headers and the drawer focus/Back coordinator. Avoid a second generic widget library that needlessly wraps unchanged Flutter components.

Component theme ownership should include AppBarThemeData, FilledButtonThemeData, OutlinedButtonThemeData, TextButtonThemeData, IconButtonThemeData, FloatingActionButtonThemeData, CardThemeData, ChipThemeData, DialogThemeData, ListTileThemeData, MenuThemeData/MenuButtonThemeData, DropdownMenuThemeData, NavigationDrawerThemeData, NavigationRailThemeData, DrawerThemeData, BottomSheetThemeData, SliderThemeData, SwitchThemeData, CheckboxThemeData, RadioThemeData, SnackBarThemeData, InputDecorationThemeData, TabBarThemeData, ProgressIndicatorThemeData, TooltipThemeData, BadgeThemeData, SearchBarThemeData and SearchViewThemeData. Prefer the SDK's correct M3 defaults; explicitly set properties that encode product policy or repair an identified mismatch. Unused component themes can remain defaults until the components are introduced.

The following is a **skeleton Dart design sketch**, not a production patch or a claim of compiled validation. It illustrates resolved theme policy; translation, persistence, dynamic-color adapter, full ThemeExtension implementations and adaptive presenters are omitted intentionally.

Theme extensions should implement `copyWith` and `lerp` so animated theme changes remain coherent. A semantic warning palette can derive from an orange seed per brightness, then be tested/harmonized without changing warning meaning. 2. **Density vs accessibility:** product intent calls for information density; M3 allows compact content. Keep text/content compact through tokens, not by shrinking action hit areas. The dense-mode switch itself must remain reachable at 48dp even when dense mode is active.
3. **Shape/version mismatch:**20dp is a current official token and required for bubbles; a blanket search/replace to 16/28 would violate product intent.18/24/6/10dp rectangular shapes need deliberate mappings. Extra-large/optical exceptions must be named and justified rather than hidden in individual widgets.
4. **Color/elevation:** black mode is an approved intentional deviation from ordinary seeded neutral surfaces. Recompute/test contrast and separation, but preserve OLED black. Do not apply primary on primaryContainer; current user bubble correctly uses onPrimaryContainer. Do not add deprecated tint overlays or arbitrary elevation shadows.
5. **Navigation recommendations:** five width classes inform spacing, field bounds, dialogs and panes. `docs/ref/md3/components__navigation-drawer__guidelines.md` opening Note recommends expanded rail specifically for Expressive adopters; this audit selects supported baseline M3 and preserves the product sidebar. They do not mandate discarding the RikkaHub layout or changing the app-specific 1000dp dock threshold. The optional right context panel and navigation rail are later design choices, not prerequisites for this migration.
6. **Input origin:** width is not the same as desktop input. A resizable desktop window can be compact; a tablet can have a mouse. Dispatch context menus using the actual secondary-click/long-press origin and maintain the common showActions behavior.
7. **Transient feedback:** making actual-compression errors into toast/dialog interruptions would contradict the product specification. Improve indicator access without automatically opening dialogs or speaking every streaming event. Preserve Back's intentional double-press message/window.
8. **System scaling and rendering:** do not flatten nonlinear accessibility scaling; watch base and user font size should compose with it. Markdown dependency styles beyond app-owned baseTextStyle require rendered verification for headings, code, links, tables and images. This audit reviewed the app-owned integration, not every dependency source or platform text engine.
9. **SDK/reference gap:** Flutter default M3 widgets can implement baseline tokens while the site leads with Expressive variants. Do not recreate unsupported Expressive components merely to look novel. Track current `year2023` opt-ins and future removals against the actual SDK version.
10. **Scope:** migration should stay inside `app/` plus specifically authorized design documentation. No backend/API rename is needed for any recommendation here. Existing HTTP/SSE field names, routes and events must remain intact.
